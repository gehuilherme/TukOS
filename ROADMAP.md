# Roadmap do TukOS

| # | Subprojeto | Resultado demonstrável | Status |
|---|---|---|---|
| 0 | Infraestrutura: repositório, build, QEMU, CI, `AGENTS.md`, `CLEAN_ROOM.md`, harness de conformidade | `cargo xtask run` dá boot numa VM | ✅ mínimo (build/QEMU/CI/docs + harness de conformidade prontos) |
| 1 | Kernel base: boot UEFI, memória, interrupções, scheduler, syscalls | kernel roda e alterna threads | ✅ feito |
| 2 | Executivo: object manager, processos, I/O manager, registro | processos e handles estilo NT | 🟡 parcial (object manager + processos/handles + **console de entrada**: teclado PS/2, `NtReadFile` bloqueante com eco e `ReadFile`/`ReadConsole`; + **leitura de arquivos**: initrd embutido read-only, `NtTukosOpenFile`/`NtReadFile` de arquivo, seek/tamanho e `CreateFileW`/`ReadFile`/`SetFilePointerEx`/`GetFileSizeEx` no `kernel32`; + **gestão de processos**: `NtTukosCreateProcess`/espera/exit code e `CreateProcessA`/`WaitForSingleObject`/`GetExitCodeProcess` no `kernel32` (um programa cria outro do initrd, espera e lê o exit code); **linha de comando ao filho**: `CreateProcessA` passa `lpCommandLine` -> `ProcessParameters` -> `GetCommandLineA/W` -> `argv` do CRT; **faltam** pipes, exec de disco real, reciclagem de slots de thread, escrita de arquivos, diretórios, FS/driver reais e registro) |
| 3 | `ntdll` + loader de PE | `.exe` de console do Windows roda sem modificação | ✅ feito (loader de imports em modo usuário, exports/ordinais/forwarders; `.exe` **real do MSVC compilado com o CRT estático** `/MT` roda sem modificação e confere byte-a-byte com o Windows real) |
| 4 | Subsistema Win32: `kernel32`, `user32`, `gdi32`, gerenciador de janelas | programa com janela abre | 🟡 início (`kernel32` mínimo: `GetStdHandle`/`WriteFile`/`ExitProcess`/`GetProcessHeap`/`HeapAlloc`/`HeapFree` + heap de usuário; superfície do CRT (TLS/FLS/locks/cookie/HeapSize) pronta; **primeiro marco de janela atingido**: um programa Win32 GUI real (`hello_win.c`, MSVC `/MT`) abre uma janela e pinta retângulo + texto "Hello, TukOS!" via `user32`/`gdi32` próprios + syscalls de GDI no framebuffer, verificado pelo kernel lendo o framebuffer (ktests `window_paints`/`gui_hello_window`) e visível com `cargo xtask run gui`; **a janela agora é interativa pelo teclado**: o teclado entrega `WM_KEYDOWN`/`WM_CHAR` ao WndProc (`NtUserGetKeyEvent` bloqueante no kernel + `GetMessageA`/`TranslateMessage` em `user32`) e o que se digita aparece na janela (`test_type.exe`, demo: `cargo xtask run gui-type`; Backspace apaga, Enter/ESC saem), verificado pelo kernel lendo o framebuffer (ktest `window_keyboard_echo`). **Nota de semântica:** `user32!GetMessageA` agora é BLOQUEANTE — um programa GUI que nunca chama `PostQuitMessage` espera por entrada em vez de sair; **a janela agora também tem MOUSE**: mover/clicar/arrastar entrega `WM_MOUSEMOVE`/`WM_LBUTTONDOWN`/`WM_LBUTTONUP` (+ botões direito/meio) ao WndProc (mouse PS/2 -> `InputEvent` unificado -> `NtUserGetInputEvent` -> `GetMessageA`), e um app de paint desenha com o mouse (`paint_win.exe`, demo: `cargo xtask run gui-paint`; arrastar deixa a trilha), verificado por pacotes injetados + leitura do framebuffer (ktests `window_mouse_click`/`gui_paint_window`); **o cursor de mouse agora é VISÍVEL**: o kernel desenha o sprite de seta, que acompanha o mouse e fica por cima sem corromper o conteúdo da janela (save-under), em qualquer demo (`cargo xtask run gui` / `gui-type` / `gui-paint`), verificado pelos ktests `cursor_save_under` + `cursor_follows_mouse`; **faltam** backbuffer por janela/compositor, múltiplas janelas, z-order, foco, hit-testing, formas de cursor customizadas (`SetCursor`/`LoadCursor` reais), roda (scroll), duplo-clique, auto-repeat, teclas de função/combinações e GDI mais rico (linhas, bitmaps, fontes)) |
| 5 | Modelo de drivers WDM/KMDF | driver `.sys` real carrega | ⬜ pendente |
| 6 | Drivers e sistemas de arquivos: NVMe/AHCI, NTFS/FAT, USB, rede, vídeo | instala e roda em hardware real | ⬜ pendente |
| 7 | Shell, desktop, instalador, privacidade | usável no dia a dia | 🟡 shell/terminal mínimo; desktop pendente (design já esboçado) |

**Legenda:** ✅ feito · 🟡 em andamento/parcial · ⬜ não iniciado.

**Marco atual:** **o cursor de mouse aparece na tela do TukOS** (`cargo xtask run gui`/`gui-type`/`gui-paint`: a seta acompanha o mouse e fica por cima da janela sem estragar o conteúdo; `cursor_save_under`/`cursor_follows_mouse` conferem). Antes: **uma janela Win32 reage ao mouse no TukOS** (`cargo xtask run gui-paint`: arraste o mouse e a janela desenha a trilha; `gui_paint_window` confere o framebuffer). Antes: **uma janela Win32 reage ao teclado no TukOS** (`cargo xtask run gui-type`: digite e o texto aparece na janela; `window_keyboard_echo` confere o framebuffer). Antes: **um programa Win32 GUI abre uma janela e pinta no TukOS** (`cargo xtask run gui`: `hello_win.exe`, compilado com MSVC, cria a janela, roda o laço de mensagens e pinta fundo + retângulo + "Hello, TukOS!"; o ktest `gui_hello_window` confere os pixels no framebuffer). Antes disso: **o TukOS boota num terminal interativo**: `cargo xtask run` cai no prompt `tukos> `, você digita um comando com argumentos (`hello`, `echo teste` imprime `teste`, `help`, `exit`) e ele roda (o shell cria o processo `<cmd>.exe` do initrd, espera, e volta ao prompt; comando desconhecido avisa). Marco 1 praticamente atingido do lado do `.exe` — boot no QEMU (0, 1) + `.exe` de console **real do MSVC com CRT completo** (`hello.c` via `printf`, `/MT`) roda no TukOS e confere stdout + exit code com o Windows real (harness: ntdll, kernel32, heap, crt, echo, fileio, spawn). **O teclado funciona**: as teclas ecoam na tela e um programa lê o stdin (o shell lê a linha com `fgets`; **comandos recebem argumentos** (linha de comando -> `GetCommandLine` -> `argv`): `echo.exe teste` imprime `teste`, conferido com o Windows real) — base de um terminal interativo. **Arquivos podem ser lidos**: `fileio.exe` (`/MT`) faz `fopen`/`fread` de `cat.txt` (initrd) e imprime o conteúdo, idêntico ao Windows real. **Processos podem criar processos**: `parent.exe` (`/MT`) faz `CreateProcessA("child.exe")`, espera e imprime o exit code do filho (`filho saiu com 42`), idêntico ao Windows real. Partes de 2 (object manager, processos, console de entrada/saída) e de 4 (`kernel32` com superfície do CRT + heap) prontas.

**Em aberto:** escrita de arquivos, diretórios (`FindFirstFile`), `NtCreateFile` completo, FS/driver reais (subprojeto 6) e registro (resto do subprojeto 2); pipes para o filho e exec de disco real; edição de linha/histórico e desktop; teclado por IRQ1 e edição de linha rica; gerenciador de janelas, múltiplas janelas, auto-repeat, teclas de função/combinações e GDI mais rico (resto do 4).
